# AviCore Admin 1.0.266 — duty storage repair

Completed 2026-09-11. Published to https://avicore-admin.web.app.

Database size: 546,966,675 → 214,600,851 bytes. Duty table including indexes: 440,582,144 → 108,150,784 bytes. Units shown to the user are decimal MB.

439,874 deleted duty rows were backed up to `private-data/duty-storage-2026-09-11T07-28-35-171Z/deleted-duty.ndjson.gz` (43,345,405 bytes). The archive was decompressed and parsed, checked for duplicate UUIDs, and its row count and latest modification/deletion timestamps matched the source database. REST count and a sorted UUID SQL aggregate timed out; verification used the direct SQL count and timestamps instead. The archive content SHA-256 is `6c2151cb7991da9b129678f1b4fcd73d59909b658bf6551ab3eed1eb0460ca7b`. `manifest.json` and `verification.json` accompany the archive. The earlier 07:26 backup directory is an interrupted, incomplete attempt and must not be used for restoration.

Only deleted rows' `entry_json` was compacted to `{}` in batches of 20,000. UUIDs, tenant ownership, pilot/date fields, deletion timestamps and modification timestamps remain. `VACUUM (FULL, ANALYZE)` returned the physical space. No active duty records were removed. Before/after active count is 17,317, and the ordered UUID/payload MD5 digest is unchanged: `981763f801640172f4d9299d17f37de7`.

The database trigger compacts future deleted payloads, including those sent by older clients, and preserves a tombstone when an older or equal-timestamp update attempts to overwrite it. It is SECURITY INVOKER, fixes search_path, and is not directly executable by anon/authenticated roles. An explicitly newer edit still follows existing synchronization semantics. The deleted UUID rows remain for offline synchronization; this is not a policy to purge all tombstones.

Web Admin import now matches unchanged entries as a multiset and retains their UUIDs/timestamps. Appending a day or correcting one entry only inserts new/changed entries and marks obsolete entries deleted. Manual entries on imported dates are still superseded. Desktop/Android installers were not rebuilt; their writes receive the database compaction protection.

Validation: 103 tests across the main application's seven src test files passed; Admin production build passed. Transactional database checks verified compaction preserves timestamps and stale updates cannot revive a tombstone, then rolled back. Both Firebase publishes succeeded; the final live HTML matches the final build and the main bundle includes 1.0.266. Authenticated browser import was not exercised against production pilot records. The broad root test command also discovers a separate avicore-test tree with missing browser globals and unrelated LINE/Knowledge failures; it is not fully green.

Security advisors reported findings in existing objects (including SECURITY DEFINER RPC exposure, mutable search_path on hazard_tolerability, pg_net placement and auth password protection); no finding named the new compaction function. Review separately: https://supabase.com/docs/guides/database/database-linter?lint=0028_anon_security_definer_function_executable and https://supabase.com/docs/guides/database/database-linter?lint=0011_function_search_path_mutable . No unrelated security policies were changed.

Rollback: the prior Admin dist and package files are in `private-data/pre-duty-storage-1.0.266/`. They can be published through a temporary Firebase hosting config pointing to that saved dist. To restore historical deleted payloads, first disable/drop the compaction trigger in a controlled maintenance window; otherwise it will immediately compact restored payloads. Restore only matching still-deleted UUIDs from the verified archive, with timestamp checks to protect newer changes. A rollback of the web release does not require restoring deleted payloads. Re-enabling full payload storage will increase database usage again. The backup is local and must be retained securely.
